# Verified audit addendum, 2026-09-10 (on the Spark)

Supplements [`../docs/ARCHITECTURE.md`](../docs/ARCHITECTURE.md), which audited commit `96f92a6` on the
Windows box. This one was taken on the DGX Spark with `torch` installed and the test suite actually
running. **Where this file and `ARCHITECTURE.md` disagree, this file is newer.**

Everything here is cited to `file.py:line` and most of it was confirmed by running the code. Items marked
**NEW** are not in `ARCHITECTURE.md`.

## Corrections to the existing audit

**The 54.4M ungradiented parameters are unwired layers, not an untrained plan decoder.** `ARCHITECTURE.md`
attributes them to "only plan step 0 reaches the loss". The count is right, the cause is not. Measured at
the real training shape under a loss touching *every* output including every plan step, 54.3M of 315.7M
are unreachable from the architecture itself:

| params | tensor | why |
|---|---|---|
| 51.20M | `reasoning_head.action_memory_embedder.weight` | declared `model.py:56`, referenced nowhere else |
| 2.10M | `reasoning_head.action_fusion.weight` | declared `:57`, used `:64`, only when `prev_plan_embeddings is not None`, i.e. only from reasoning pass 2 |
| 1.05M | `decoder.intent_proj.weight` | declared `:152`, referenced nowhere else |

The plan-sequence heads (`type_head`, `source_head`, `target_head`) are **not** in that list; they receive
gradient whenever the loss includes the plan steps. So D3's "train every plan step" is a change to the
**loss in `student.py`**, not to the model. Detail in [`SPARK_BRINGUP.md`](SPARK_BRINGUP.md).

**The two `torch.device("cuda")` violations have changed form, not gone away.** `student.py:34` and
`teacher.py:37` now write `torch.device("cuda" if torch.cuda.is_available() else "cpu")`. Correct here by
luck; silently selects CPU instead of XPU on the Windows box. **NEW:** `MTG_bot/utils/device.py` is
imported by exactly one file in the repository, `tools/latency/bench.py:60`. Nothing under `MTG_bot/` uses
the mandated helper at all.

**The rule-engine test count has moved.** `ARCHITECTURE.md` records 1 pass of 22, and protocol check P7
records 10 passed / 29 failed at `bc14850`. Twenty of those failures were one stale method name. After
migrating the seven test modules onto `game_initializer.initialize_game_state`, the full suite is
**17 passed / 22 failed** and `rule_engine` alone is **10 passed / 16 failed**. P7 still fails.

## NEW, and severe: generic mana is effectively free

Two different rules for one cost. `engine.py:82-95` `_can_pay_cost` is **correct**: colour requirements
from matching mana, then the generic part from any remaining mana. The actual payment at **`engine.py:216`**
is `for mt, amt in cost.items(): mp[mt] = mp.get(mt, 0) - amt`, which subtracts the generic amount from a
**"Generic Mana" pool slot that no land ever fills**.

Measured, Azusa Lost but Seeking, cost `{2}{G}`, with exactly 3 green in the pool:

```
pool before       green=3, generic=0
_can_pay_cost     True
pool after paying green=2, generic=-2
```

A three-mana spell consumed one mana. **Two of every three mana in that cost was free.** Every curve,
tempo and hold-up decision any policy has ever learned here was learned against the wrong economy, and
`CastSpellAction` is only 0.5% of decisions partly because the rest of targeting is broken, not because
casting is expensive.

## NEW: the engine cannot report that it failed

`engine.py:185-189` wraps legal-move generation in `except Exception -> logger.error` and then **returns
the partially built list**. `engine.py:278-279` makes `execute_move` return `[f"Error: {e}"]`. So a
truncated legal-move list and a failed rules operation are both indistinguishable from success.

This is the one that makes everything else unverifiable. Protocol check P8 wants `engine_error_rate == 0`
on a smoke slate; nothing can compute it, because errors are not raised and `environment.py:153` discards
the event list anyway. Until the engine raises a typed error, "correctness before strength" cannot be
gated and **no strength number from this engine, past or future, is falsifiable.**

## NEW: the stack discards its own payload

`resolve_stack` never reads `StackItem.effect_data` (`engine.py:281-298`); it calls
`resolve_spell_effects` with the source card only. So a resolving **triggered ability re-runs the source
card's whole effect list** instead of the trigger, does nothing, and re-enters the permanent onto the
battlefield, re-setting summoning sickness.

## NEW: targeting fails permissively, not just silently

`ARCHITECTURE.md` has the silent-no-op half: 117 card rows emit `{"type":"selector"}`
(`card_data_parser.py:160`) while both consumers read `effect.get("target")` (`effect_handlers.py:111`
and `:126`). The other half is worse. For the cards that *do* carry a top-level `target` key,
`TargetFilter`'s dict branch (`target_filtering.py:28-63`) never inspects `type` or `filter` and
**returns True for every permanent and both players**. Village Rites offered the opponent's creature and
both players as legal targets, and the node being read is an additional-cost sacrifice, not a target.

Legality must become a single oracle the engine asserts against, not a filter that defaults to yes.

## NEW: other rule-engine defects

- **`MTG_bot/main.py` is entirely dead.** It calls five things that do not exist:
  `game_initializer.get_available_game_modes` (`:214`), `get_available_decks` (`:227`),
  `_load_decklist_from_db` (`:245-246`), `engine.mulligan` (`:262`),
  `engine._check_win_loss_conditions` (`:339`).
- **Commander support is a single write-only boolean.** `game_initializer.py:81-88` sets `is_commander`
  and grep confirms nothing reads it. No command-zone casting, no commander tax, no commander damage, no
  death-to-command-zone replacement, no Stack zone entity. In the priority format.
- **Two incompatible player-construction paths**, and the unused one omits the Command Zone:
  `game_graph.py:77-96` creates 5 zones at 20 life, `game_initializer.py:64-100` creates 6 including
  Command at 40 life for Commander.
- **Tokens are invisible to combat.** `effect_handlers.py:143-155` gives a token `type_id` 999, and
  `combat_handlers.py:29, :66, :102` look up `get_creature_stats(card.type_id)`, so tokens and any
  creature whose printed power is not a plain integer are filtered out of combat entirely.
- **`get_legal_moves` is nondeterministic and does a 397-row SQLite read per call.** `engine.py:110-119`
  constructs a fresh `CardDataLoader` inside the MakeChoice branch and `random.sample`s five card names
  at `:116`. The legal action set for an identical state differs between calls.
- **`Controlled By` is one relationship type used in two directions for two meanings.** player->zone
  "owns this zone" (`game_graph.py:94`, `game_initializer.py:74`) versus player->card "controls this card"
  (`game_initializer.py:86, :96`, `game_graph.py:121`). Read backwards at `combat_handlers.py:112`, which
  is the lifelink bug. `test_keywords.py:45` builds creature->player, so the test is **structurally
  incapable of catching it** even once the test is otherwise repaired.
- **Leaving the battlefield is always reported as entering the acting player's graveyard**
  (`engine.py:268-274`), regardless of where the permanent went or who controlled it.
- **Damage to blockers bypasses `apply_damage`.** `combat_handlers.py:131` and `:138` do
  `damage_taken +=` directly while `:119` routes unblocked damage through `effect_handlers.apply_damage`,
  so protection and replacement effects apply to unblocked damage only.
- **No deathtouch, trample, menace, defender, first strike or double strike**, and no first-strike damage
  step in `engine.py:306`'s phase list. The one first-strike check present looks up a vocabulary name that
  does not exist.
- **There is no interaction.** Measured over a full game: 741 of 794 decisions belonged to the active
  player, and all 53 non-active decisions were in Declare Blockers (`engine.py:126-136`). A policy trained
  to convergence here has never been punished for tapping out.

## NEW: the PPO update is void, three independent reasons stacked

Not "learns slowly". Diverges.

1. **Dropout is active during collection.** 64 active dropout modules plus `train()` mode at
   `student.py:102` give an **8.6-nat spread in log pi on identical input**, so the importance ratio spans
   0.0002x to 5462x with *zero* policy change.
2. **The proactivity bias is applied asymmetrically.** Up to 10 nats added to collection-time logits
   (`student.py:126-129`) and none at training time (`:180-181`).
3. **The buffer is never cleared** (`student.py:19-27`, `train.py:411-412`), so ratios are taken against
   policies up to 1,000 episodes old.

With a negative advantage `torch.clamp` does not bound the surrogate, and there is no gradient clipping.
Measured grad norms at full scale run **663 to 1744**. Fix 1 and 2 together by storing tokens plus mask
and recomputing the old log-prob under `eval()`, which `DESIGN_ACTION_SPACE.md` section 4.3 already
prescribes.

## NEW: full-game BPTT is not memory-feasible at the configured scale

`student.py:156-196` retains a measured **263 MB of activations per transition** and backpropagates once
per episode. So 200 transitions costs 54 GB, and the configured 10,000 (`config_rl.py:9`) costs
**2,633 GB against 121 GB of unified memory** — an OOM at roughly **450 transitions**, in a format where a
measured game was still running at 2,000 steps and turn 91.

This does not overturn D6, it sharpens it. D6 says memory does not decide the question because step-level
gradient checkpointing costs about 141 KB per decision. That is true *of the design*; the current code
does not do it. Checkpointing or truncation is a **prerequisite** for any run past a few hundred steps,
not an optimisation.

## NEW: the do-nothing problem is worse than recorded, and the reward agrees with it

`ARCHITECTURE.md` records the benchmark paying a do-nothing policy 0.900 on "Level 2". Measured at HEAD:
**1.000 on all 25 level_1 survival puzzles** as well, because `benchmarker.py:82-108` never reads
`p2_attacking_creatures` or `p1_mana`, and `:156-163` scores proximity as a fraction of starting life.

The shaping reward agrees with the broken metric: do-nothing accrues exactly **+0.00** while an active
policy accrues **-5.36 over 200 steps** and **-181.61 over 2,000**. So the four anti-passivity mechanisms
bolted on top are fighting the reward function, not the agent.

## NEW: blocking is attributed to the wrong agent, and it is a handful of lines

`engine.py:132-136` swaps priority to the defender to enumerate blocks and restores the attacker at
`engine.py:188`. So `obs['active_player']` (`environment.py:257`) names the **attacker**, and
`train.py:145` attributes the decision to the wrong agent. Measured at step 596 of a live game: the frozen
model chooses the student's blocks and the transition is stored nowhere. **The student has never received
one gradient on a block of its own**, and in the mirror case it is trained to block badly for the opponent
against a P1-centric reward.

## NEW: the self-play distribution is capped at mana value 3 forever

`train.py:111` omits `total_games`, so `teacher.py:54-56` pins `max_cmc=3` permanently.
`deck_generator.build_from_sequence` does no singleton dedup and shuffles before `game_initializer.py:82`
takes `deck[0]` as the commander, so the commander is a random card and often a basic land.
`state_converter.py:81-101` has no command-zone encoding at all. The charter's rank-1 niche-deck clause
cannot be practised from a pool that excludes every card above three mana.

## NEW: six test files collect zero tests

`scenarios/test_complex_targeting.py`, `test_generalized_effects.py`, `test_static_effects.py`,
`test_temporary_effects.py`, `strategic_brain/test_self_play.py`, `test_visualizer_live.py`. They define

## The action-side surface for rank 1(b) does not exist

The 65-float descriptor (`environment.py:247-249`, built at `state_converter.py:103-141`) carries no card,
instance, controller or phase identity. Two Forests differ only in a creation-order timestamp at dim 17,
and every `MakeChoiceAction` in a menu is the identical vector because `action_mapper.py:46` reads
`card_id`/`blocker_id` and `MakeChoiceAction` has neither. The board side *does* carry identity through
`CardEmbedder`, but **there is no index linking an action to its board token**, so a card's learned
encoding cannot reach the decision that plays it.

D3's preserved tokenizer exists but is wired to the wrong index space: `action_mapper.py:201-210` claims
in a comment to match `state_converter`'s order and agrees on **11 of 214 positions**; `tokens_to_action`
hardcodes `player_id=active_player_id`, so **0 of 2 legal moves survived a measured round trip**. A
round-trip property test over the legal-move set (`DESIGN_ACTION_SPACE.md` section 8.2) costs an hour and
would have caught all three.
